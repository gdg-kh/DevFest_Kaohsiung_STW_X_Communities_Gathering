# GDG Kaohsiung 2026 官網 — 文件索引

## 這些檔案怎麼用

- **`design/`** 是給人看的規格，決策與理由都在這裡。開工前讀一次，之後當參考。
- **`tasks/`** 是給模型吃的施工單，共 31 份。**每份都是自足的**——
  整份貼進新對話即可，不需要再貼 design 或其他任務。
  每份末尾有**該任務專屬的驗收條件**，逐條對照才算完成。
  這些檔案由 `build-tasks.mjs` 產生，不要手動修改。

不要把整份設計文件貼給模型。施工單裡已經萃取出該任務需要的規格，
多貼只會稀釋注意力，讓小模型更容易跑題。

## 自動檢查

```bash
npm run check:2026
```

`2026/scripts/check.mjs` 把能自動驗的驗收條件跑成一支指令：

- 資料面：id 唯一性與格式、講者與議程的雙向關聯、群組與軌道是否存在、
  時間格式與同軌道重疊、群組色是否為 GDG 官方色、
  JSON 有沒有混進圖片路徑欄位、圖片檔是否存在
- 程式面：`innerHTML`、`var`、寫死的外部網址、用 `new Date()` 解析議程時間、
  tokens.css 以外的 hex 色碼、`font-weight` 超過 700、
  「GDG Lead」字樣、載入中文 webfont、替代字體
- 產生物：`share/` 底下有沒有 JSON 已刪除的殘留資料夾

有 error 時退出碼為 1，可以掛進 CI 或 pre-commit。
警告不擋上線（例如圖片還沒放）。

**這支腳本不取代人工驗收**。版面、鍵盤操作、手機實機、
彈窗焦點鎖定這些還是要照施工單裡的驗收條件自己走一遍。

## Git Flow 施工流程

已有 `develop`。每個任務一條 feature 分支：

```bash
# 1. 開分支（分支名寫在每份施工單的開頭）
git checkout develop
git pull
git checkout -b feature/T05-i18n

# 2. 開一個新對話，整份貼上 docs/tasks/T05-i18n.md
#    把模型輸出的檔案存到指定路徑

# 3. 驗收（施工單末尾有清單）
npx serve 2026          # 本機預覽，不能用 file:// 開
npm run lint
npm run format:check

# 4. 合回 develop
git add .
git commit -m "feat(2026): add i18n module"
git checkout develop
git merge --no-ff feature/T05-i18n
git branch -d feature/T05-i18n
```

### 幾個實務建議

**一個任務一個對話。** 施工單是自足的，開新對話反而更乾淨。
同一個對話做多個任務時，前面的程式碼會佔住 context，
小模型容易把 A 檔案的寫法帶到 B 檔案。

**驗收不過就重來，不要在同一個對話裡反覆修。**
小模型改到第三輪通常會愈改愈亂。
把失敗的點加進要求裡（例如「不可以用 innerHTML」），開新對話重跑一次。

**規格改了要改在源頭。** `docs/tasks/` 底下的檔案是**產生出來的**，
要改共用內容請改 `gdgkh-2026-build-prompts.md`，然後：

```bash
node docs/build-tasks.mjs
```

直接手改 `tasks/*.md` 的話，下次重新產生就會被蓋掉。
這也是 SDD 的核心動作：**驗收失敗時先問「是程式沒照做，還是規格沒寫清楚」**，
如果是後者，改規格再重跑，同樣的錯才不會下次又發生。

**T19、T20 是例外。** 這兩個要接續改同一個 `editor.html`，
需要把上一版整份貼回去，所以檔案會很大，建議用能力較強的模型做。

**產生器（T21、T22）要在有真實資料後才跑。**
假資料階段先確認程式跑得起來即可，圖片不存在會走預設圖，不會中斷。
